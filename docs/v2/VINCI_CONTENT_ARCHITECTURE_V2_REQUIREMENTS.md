## 3. V2.0 总体目标

我要把 Vinci 网站建设为一套以 PostgreSQL 为核心的在线内容管理系统，用于管理：

- Wiki 知识库和技术教程；
- 新闻文章；
- 成员资料；
- 草稿、审核、发布和历史版本；
- 图片和其他媒体元数据；
- Markdown 快照导出；
- 我在本地修改 Markdown 后提交的内容提案。

系统同时支持两条内容创作路线：

```text
在线修改
→ 数据库草稿
→ 审核
→ 数据库正式版本
→ 前台立即生效
```

```text
我在本地修改 Markdown
→ 提案分支和 Pull Request
→ CMS 冲突检查
→ 导入数据库草稿
→ 审核
→ 数据库正式版本
→ 前台立即生效
```

两条路线必须汇入同一套数据库草稿、审核和发布系统。

## 4. 不可改变的核心原则

### 4.1 PostgreSQL 是线上内容的唯一权威来源

正式切换完成后，以下数据全部以 PostgreSQL 为准：

- 新闻；
- Wiki；
- 成员资料；
- 正式 Markdown 原文；
- Frontmatter；
- 正式版本历史；
- 当前正式版本指针；
- 草稿；
- 审核状态；
- 删除和恢复记录；
- 编辑锁；
- 审计日志；
- 导出和导入状态。

前台运行时不得依赖 GitHub Markdown 作为正式数据源。

### 4.2 代码仓库与内容仓库分离

代码仓库继续使用：

```text
SDUTVINCI/sdutvinci_web
```

代码仓库保存：

- Nuxt、Vue 和 TypeScript；
- CMS 页面和 API；
- 数据库 Schema 和 Migration；
- 编辑器和 Markdown 渲染组件；
- Docker、GitHub Actions 和运维脚本；
- 测试和技术文档。

独立内容仓库已由维护者建立：

```text
SDUTVINCI/sdutvinci_content
```

原代码仓库的 `content/` 已由维护者完成首次完整复制。该复制只作为初始可读快照和后续接管基线，不代表自动导出、确定性序列化、稳定 ID、Manifest、Snapshot 或数据库权威切换已经完成。

内容仓库保存：

```text
news/
wiki/
members/
.vinci/snapshot.json
manifest.json
README.md
```

内容仓库只承担：

- PostgreSQL 自动导出的可读 Markdown 快照；
- 我克隆到本地后阅读和整理全部内容；
- 我在本地修改或新增 Markdown 的工作区；
- 通过提案分支和 Pull Request 向 CMS 提交修改；
- 空数据库首次初始化；
- 灾难性恢复材料；
- 管理员明确确认后的人工导入来源。

内容仓库不承担：

- 网站运行时读取；
- 自动覆盖生产数据库；
- 直接决定线上正式版本；
- 触发代码镜像重新构建；
- 正常服务器迁移的完整备份。

### 4.3 内容仓库 `main` 的写入规则

- `main` 只允许数据库导出机器人写入。
- 数据库导出使用普通 Commit，不 Force Push，不改写历史。
- 我在本地修改内容时使用 `proposal/*` 分支。
- 提案 PR 不直接 Merge 到 `main`。
- PR 只是修改提案和 Diff 载体。
- CMS 导入 PR 后只创建草稿、移动提案或删除提案，不能直接发布。
- 正式发布后由数据库重新导出并更新内容仓库 `main`。

### 4.4 GitHub 故障不能阻止数据库发布

正式切换后，发布事务必须先完成数据库正式版本。

GitHub、网络或内容仓库发生故障时：

- 数据库发布仍然成功；
- 前台仍然立即显示新内容；
- 导出任务进入等待、重试或失败状态；
- 后台向管理员显示同步异常；
- 修复后可以重试；
- 不回滚已经成功的数据库正式版本。

### 4.5 正常导入不能覆盖整个数据库

正常情况下只允许根据：

- Pull Request Diff；
- 原始快照基线；
- 稳定文章 ID；
- 数据库当前 Revision；
- 本地提案内容；

执行逐项导入。

不得因为本地仓库缺少某篇文章，就自动删除数据库中的文章。

不得把整个本地目录视为数据库最终状态。

## 7. 数据库正式内容模型

### 7.1 `articles`

用于保存文章稳定身份和当前状态，至少包含：

- `id`：永久 UUID；
- `collection`；
- `relative_path`；
- `public_path`；
- `title`；
- `current_revision_id`；
- `published_at`；
- `deleted_at`；
- `created_at`；
- `updated_at`。

文章标题、文件名或路径发生变化时，文章 UUID 不变化。

### 7.2 `article_revisions`

正式版本不可变，至少包含：

- `id`；
- `article_id`；
- `revision_number`；
- `markdown_source`；
- `body`；
- `frontmatter`；
- `content_hash`；
- `published_by_user_id`；
- `reviewed_by_user_id`；
- `restored_from_revision_id`；
- `created_at`。

规则：

- 每次正式发布都插入新 Revision；
- 已存在 Revision 不允许业务层更新正文；
- 恢复旧版时复制旧内容并生成新 Revision；
- 历史查看和 Diff 以数据库 Revision 为准；
- Git Commit 不再是线上版本主键。

### 7.3 草稿基线

草稿应使用：

- `base_revision_id`；
- `base_content_hash`；
- 乐观锁版本号；

判断草稿是否基于当前正式版本。

### 7.4 导出 Outbox

`content_export_jobs` 必须与正式发布写入同一 PostgreSQL 事务，至少记录：

- 目标类型；
- 目标 ID；
- Revision ID；
- 操作类型：新增、更新、移动、删除、成员更新；
- 状态；
- 尝试次数；
- 下次重试时间；
- 最后错误；
- 创建和完成时间。

### 7.5 导入记录

本地 PR 导入至少记录：

- 仓库；
- PR 编号；
- Base Commit；
- Head Commit；
- 发起人；
- Dry Run 结果；
- 每个文件的处理状态；
- Base Revision；
- Current Revision；
- Proposed Hash；
- 是否自动合并；
- 冲突原因；
- 创建的草稿或提案 ID；
- 操作审计。

## 8. 在线发布事务

正式切换到数据库权威后，同一个事务必须完成：

```text
锁定并验证草稿
→ 检查审核状态
→ 检查 base_revision_id
→ 构建确定性 Markdown
→ 插入 article_revision
→ 更新 articles.current_revision_id
→ 更新草稿状态
→ 写发布记录
→ 写审计日志
→ 写 content_export_jobs
→ 提交事务
```

事务提交后：

- 前台下一次请求即可读取新版本；
- 不等待 GitHub；
- 不等待 Actions；
- 不重新构建镜像；
- 不重启应用；
- 导出由后台 Worker 异步完成。

## 9. 我在本地修改 Markdown 的流程

### 9.1 本地工作

```bash
git clone <内容仓库>
git switch -c proposal/update-ros2-tutorial
```

我可以在本地：

- 阅读全部知识库；
- 修改一个或多个教程；
- 新增教程；
- 整理目录；
- 修改新闻；
- 提交成员资料修改提案。

完成后：

```text
Commit
→ Push proposal/* 分支
→ 创建 Pull Request
```

### 9.2 稳定文章 ID

数据库导出的文章 Markdown 应包含：

```yaml
---
vinciId: <文章永久 UUID>
title: 示例
---
```

`vinciId` 用于识别文章，不随路径或标题改变。

### 9.3 快照基线

`.vinci/snapshot.json` 至少记录：

- `articleId`；
- `revisionId`；
- `revisionNumber`；
- `relativePath`；
- `sha256`；
- 导出时间；
- 导出格式版本。

### 9.4 三方比较

导入时比较：

```text
Base
= 我开始修改时内容仓库记录的 Revision

Current
= 数据库当前正式 Revision

Proposed
= 我在本地修改后的 Markdown
```

规则：

- `Base == Current`：可以安全导入草稿；
- `Base != Current` 且修改区域不重叠：允许尝试自动合并，但必须显示结果；
- 修改区域重叠或无法确定：必须人工解决；
- 任何情况下都不能直接覆盖正式版本；
- 导入成功只创建草稿，不自动审核或发布。

### 9.5 Git Diff 范围

只处理 PR 中明确发生的：

- 新增；
- 修改；
- 重命名；
- 移动；
- 删除。

其他成员在数据库中新建或修改但不属于该 PR Diff 的内容，不得受到影响。

### 9.6 删除

删除文件只生成删除提案。

管理员必须在 CMS 中再次确认，才能进入正式删除流程。

### 9.7 内容仓库 PR

- PR 不直接 Merge 到 `main`；
- 导入完成后可由系统写评论说明导入结果；
- PR 可以关闭；
- 正式发布后的最终 Markdown 由数据库导出到 `main`；
- 本地分支可在确认导出完成后删除。

## 10. 自动导出和凌晨对账

### 10.1 增量导出

后台 Worker：

- 周期性领取待处理 Outbox；
- 使用 PostgreSQL advisory lock 或等价机制防止重复执行；
- 将短时间内多个变更合并为合理数量的 Commit；
- 使用确定性序列化；
- 支持幂等重试；
- 记录成功 Commit；
- 失败后指数退避；
- 达到上限后进入人工处理状态；
- 不阻塞前台和发布。

### 10.2 确定性序列化

必须固定：

- Frontmatter 字段顺序；
- YAML 数组格式；
- 空值策略；
- 日期格式；
- 换行符；
- 文件末尾换行；
- Unicode 处理；
- Markdown 正文是否保留原样；
- 系统字段生成规则。

相同数据库 Revision 必须始终导出相同字节和相同 SHA-256。

### 10.3 每天凌晨 3 点全量对账

时区固定为：

```text
Asia/Shanghai
```

每天凌晨 3 点：

```text
从数据库生成完整临时快照
→ 生成 manifest 和 SHA-256
→ 拉取内容仓库 main
→ 比较新增、修改、缺失和多余文件
→ 输出报告
→ 有差异时以数据库为准生成修正 Commit
```

对账不得反向修改数据库。

### 10.4 初次导入和灾难恢复

内容仓库只允许在以下情况下反向导入：

- 目标数据库完全为空；
- 管理员明确选择“从 Markdown 初始化”；
- 先执行 Dry Run；
- 检查格式版本、稳定 ID、路径、哈希和引用；
- 显示将新增的数据；
- 输入明确确认；
- 写入审计记录。

灾难恢复必须和正常 PR 导入分开，不允许普通应用启动时自动执行。

→ Nuxt SSR
→ PostgreSQL current_revision
→ Comark 渲染
→ Vue Prose 组件

- 需要同步处理文章详情、列表、首页、Wiki 导航、搜索、RSS 和 Sitemap；
- 不得使用无法及时失效的长缓存掩盖数据库更新。

## 13. 部署、备份、恢复和迁移

本节目标是让首次部署、日常更新、备份、恢复、故障排查和整机迁移尽可能通过统一入口完成，并避免维护者记忆大量零散命令。

### 13.0 部署用户原则

取消专用 `vinci-deploy` 用户，默认直接使用执行安装的当前系统用户作为部署和运维用户。

必须满足：

- 安装器自动识别当前用户的用户名、UID、GID、Home 和默认 Shell，不写死 `tungchiahui` 或其他具体用户名；
- 所有部署脚本、systemd unit、timer、目录权限、Git 工作区、备份目录和日志目录都基于当前安装用户生成；
- 不再要求创建、切换或依赖 `vinci-deploy`；
- 不得在脚本中残留 `/home/vinci-deploy`、`sudo -u vinci-deploy`、`User=vinci-deploy` 或同类硬编码；
- 只有安装系统包、写入系统级 systemd、调整防火墙或其他确实需要的系统操作才使用 `sudo`；
- 应明确检查当前用户是否具备 Docker、目标目录、Git 凭据、备份目录和 systemd 所需权限；
- 对 Docker 组近似高权限的风险给出清楚说明；
- 从旧服务器迁移时，如果旧环境使用过 `vinci-deploy`，提供文件归属修正、定时任务迁移、systemd unit 替换和旧用户安全删除指南；
- 使用当前用户不会改变数据库、内容仓库、S3/COS、蓝绿部署和迁移包的结构，不能把用户名写入不可迁移的数据模型。

最终提供统一入口：

```bash
./vinci install
./vinci update
./vinci status
./vinci doctor
./vinci backup
./vinci restore <备份>
./vinci export-instance
./vinci import-instance <迁移包>
```

内部可以复用现有安全脚本，但维护者不应记忆大量零散命令。

### 13.1 正常完整备份

至少包括：

- PostgreSQL custom-format dump；
- 数据库 Schema / Migration 版本；
- 当前应用 Commit 和镜像；
- `.env` 和密钥的独立加密备份说明；
- 内容仓库最近同步状态；
- 对象存储配置清单；
- SHA-256 校验；
- 备份清单、创建时间、来源主机、应用版本和恢复兼容版本；
- 最近一次备份验证结果。

必须支持：

- 自动数据库备份；
- 自动配置清单备份；
- 自动内容快照或迁移清单生成；
- 自动健康检查；
- 手动立即备份；
- 备份锁，防止多个定时任务或人工任务并发执行；
- 备份完成后的完整性校验；
- 定期在隔离环境进行可恢复性验证，而不是只检查文件存在。

真实 `.env`、私钥和 Token 不得以明文进入普通备份包、日志或 Git。需要备份时，应使用维护者明确配置的加密方式或只输出可重建清单。

### 13.2 正常迁移

正常换服务器必须使用完整 PostgreSQL 备份，而不是只从 Markdown 恢复。

迁移目标是尽量做到：新服务器安装基础依赖后，通过少量配置和统一命令即可完成导入、Migration、健康检查和蓝绿启动。迁移包和教程不得依赖旧服务器的固定用户名、固定 Home 路径或 `vinci-deploy` 用户。

迁移流程至少覆盖：

- 旧服务器执行预检查和 `export-instance`；
- 校验 PostgreSQL dump、配置清单、Commit、镜像、内容仓库状态和 SHA-256；
- 将迁移包和加密密钥材料分开传输；
- 新服务器使用当前安装用户执行 `install` 和 `import-instance`；
- 修复文件属主、目录权限、systemd unit、timer 和 Docker 权限；
- 恢复 PostgreSQL、运行 Migration、检查 S3/COS、启动非活动槽位并完成健康检查；
- 切换 gateway、域名或 DNS 前后的验证；
- 保留旧服务器回滚窗口；
- 迁移成功后的旧迁移包、临时文件和敏感文件清理。

Markdown 快照不包含：

- 用户和密码哈希；
- 会话；
- 草稿；
- 审核记录；
- 完整 Revision 历史；
- 编辑锁；
- 审计日志；
- 导出和导入运行记录。

### 13.3 S3/COS

图片二进制仍以 S3/COS 为权威，至少需要：

- Bucket 版本控制；
- 防误删除；
- 生命周期策略；
- 定期对象存在性检查；
- 可选跨区域复制；
- 与数据库媒体元数据的一致性检查。

### 13.4 自动备份保留与自动清理

所有自动备份、自动部署、自动对账和日志机制都必须配套自动清理，禁止无限累积。

默认备份保留策略采用可配置的分层保留：

- 最近 7 天：每日至少保留 1 份；
- 最近 4 周：每周至少保留 1 份；
- 最近 12 个月：每月至少保留 1 份；
- 维护者可通过配置调整数量和期限，但不得默认无限保留。

自动清理至少覆盖：

- PostgreSQL 备份；
- 配置清单和迁移包；
- 内容全量快照、临时导出目录和对账报告；
- 自动部署日志、备份日志和诊断日志；
- 已无引用的旧镜像、旧构建缓存和临时下载文件；
- 已失效的候选槽位产物，但必须保留当前活动版本和至少一个已验证可回滚版本；
- 超过保留期的失败任务明细和临时错误文件，但保留必要审计摘要。

清理安全要求：

- 只有新备份成功并通过校验后，才允许按策略删除旧备份；
- 不删除当前最新成功备份、最近一次已验证可恢复备份和维护者标记为“锁定保留”的备份；
- 清理前后记录删除清单、释放空间和失败原因；
- 支持 Dry Run；
- 清理失败不能影响新备份、网站运行或数据库发布；
- 对磁盘剩余空间设置告警和保护阈值；
- 不使用宽泛危险命令删除未校验路径；
- S3/COS 生命周期策略必须与数据库和本地保留策略分别说明，禁止误删仍被正式 Revision 引用的对象。

### 13.5 自动部署维护

保留现有 GitHub Actions、完整 Commit SHA 镜像、服务器每分钟检查、蓝绿部署、健康检查和失败回滚。

同时必须：

- 自动记录每次检查、拉取、Migration、启动、健康检查、切换和回滚结果；
- 失败时保留足够诊断信息，但日志必须轮转和自动清理；
- 自动清理不再需要的旧镜像、临时文件和下载缓存；
- 始终保留当前活动镜像和至少一个已验证回滚镜像；
- 清理操作不得与正在进行的部署、备份或恢复并发冲突；
- 内容发布不得触发代码镜像部署。

### 13.6 必须提供的详细教程

最终文档至少包括：

- 从一台全新服务器开始的首次部署教程；
- 当前用户部署和权限准备教程；
- GitHub Actions、镜像仓库、Deploy Key 或细粒度 Token 配置教程；
- PostgreSQL 自动备份、手动备份、恢复和验证教程；
- 新服务器完整迁移教程；
- S3/腾讯云 COS 配置、版本控制、生命周期和检查教程；
- 内容仓库初始化现状、导出接管、故障重试和手工修复教程；
- 蓝绿部署、失败回滚和旧版本清理教程；
- 灾难恢复教程；
- 常见问题和排障 FAQ。

每份教程必须尽可能详细，并包含：

- 适用场景和前置条件；
- 命令执行用户和所需权限；
- 可复制的命令或统一入口；
- 配置项说明；
- 每一步预期结果；
- 验证命令；
- 常见失败、原因和修复方法；
- 回滚方法；
- 安全注意事项；
- 不包含真实密码、Token、私钥和生产地址的示例。

文档必须随着相关阶段真实实现同步更新，不能提前把计划写成已实现，也不能只保留过时的 V1 操作方式。

## 14. 安全要求

- 数据库是线上内容唯一权威来源。
- 内容仓库 `main` 只允许导出机器人写入。
- 本地修改通过 `proposal/*` 和 PR 提交。
- PR 只能导入草稿或提案。
- 所有导入先 Dry Run。
- 导入必须做 Base / Current / Proposed 三方比较。
- 外部工具不得直接连接生产数据库。
- 普通应用启动不得自动从 GitHub 覆盖数据库。
- 删除、移动、成员修改和高级 HTML 必须单独确认。
- 原始 HTML、Vue/MDC 的存储型 XSS 风险继续沿用可信账号、人工审核和管理员发布边界。
- 导入的外部 Markdown 不得自动发布。
- GitHub、数据库、S3、私钥和 Token 的失败信息必须脱敏。
- 所有有破坏性的测试只在隔离环境执行。
- Migration 必须兼容蓝绿部署，优先使用 expand/contract。
- 不自动执行不可逆 down migration。
- 不 Force Push 内容仓库和代码仓库。
