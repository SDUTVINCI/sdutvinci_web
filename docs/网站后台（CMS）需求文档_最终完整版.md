# 网站后台（CMS）需求文档

## 一、项目目标

我有一个 Nuxt Content 网站。

网站的大部分内容由 Markdown 文件组成。

我希望为网站开发一个后台管理系统，使普通成员无需了解 Git 或 Markdown，即可完成文章编辑和发布。

后台与网站属于同一个项目。

用户访问网站前台浏览内容。

管理员和编辑者登录后台，对网站内容进行管理。

---

# 二、文章管理

后台需要能够浏览网站中的所有 Markdown 文章。

文章至少支持：

- 查看
- 编辑
- 新建
- 删除
- 搜索
- 按目录分类浏览

能够快速定位需要修改的文章。

---

# 三、Markdown 编辑器（重中之重）

后台需要提供可视化 Markdown 编辑器。

至少支持：

- 标题
- 普通文本
- 粗体
- 斜体
- 删除线
- 引用
- 有序列表
- 无序列表
- 任务列表
- 链接
- 图片
- 表格
- 行内代码
- 代码块
- 分割线

编辑器需要支持：

- 可视化编辑
- Markdown 源码编辑

两种模式可以自由切换，并且不会破坏内容。

---

# 四、Frontmatter

后台支持编辑文章 Frontmatter。

第一版建议维护以下 Frontmatter 字段：

```yaml
title:
authors:
contributors:
updatedAt:
publishedAt:
description:
```

其中：

- `title`：文章标题，由用户填写。
- `authors`：创建文章时自动加入当前用户，也允许管理员调整。
- `contributors`：成功发布过修改的成员（不包含作者），由系统自动维护。
- `updatedAt`：每次正式发布时由系统自动更新，普通用户不可修改。
- `publishedAt`：文章第一次正式发布时自动生成，后续保持不变。
- `description`：文章摘要，可由用户填写；留空时由系统自动生成。

其中 `updatedAt`、`publishedAt` 均由系统自动维护，不允许普通用户手动编辑。

最终写入 Markdown：

```yaml
authors:
  - dongjiahui

contributors:
  - zhangsan
```

# 五、图片管理

编辑器支持：

- 将图片转webp后上传
- 上传图片至S3协议的图床。
- 拖拽图片
- 粘贴截图

上传完成后自动插入 Markdown。

后台负责管理图片。

用户无需手动填写图片链接。

---

# 六、草稿

编辑过程中支持：

- 自动保存
- 手动保存草稿

用户重新打开文章时，可以恢复未发布内容。

正式发布前，草稿不会影响网站展示。

草稿存储在 PostgreSQL 中，不写入正式 Markdown 文件，也不产生 Git Commit。

已发布文章正文的唯一正式数据源仍然是 Markdown。

---

# 七、多人编辑

后台需要避免多人同时修改同一篇文章。

当一篇文章已经有人正在编辑时：

- 能看到是谁在编辑
- 默认不能直接覆盖
- 管理员可以接管
- 编辑锁需要定时心跳
- 用户正常离开编辑页时主动释放编辑锁
- 心跳超时后自动释放编辑锁
- 管理员接管操作需要写入审计日志

---

# 八、版本冲突

如果用户编辑期间，文章已经被别人发布了新的版本。

再次发布时，应提示：

"当前文章已有更新，请重新同步后再发布。"

不能直接覆盖其他人的修改。

---

# 九、文章发布

编辑完成后支持：

- 保存草稿
- 提交审核
- 管理员审核通过并发布
- 管理员驳回并填写原因
- 提交者在审核前撤回

普通成员不能直接发布正式文章。

发布成功后，网站展示最新内容。

### 文章历史版本要求

- Markdown 文章通过 Git 管理历史版本。
- 只有管理员审核通过并正式发布文章后，才写入 Markdown、执行 Git Commit 和 Git Push，并记录操作用户、文章路径和修改说明。
- 后台应支持查看单篇文章的历史版本列表。
- 支持查看指定历史版本的完整内容。
- 支持比较两个版本之间的差异。
- 支持恢复到任意历史版本，恢复操作必须生成新的 Git Commit，不得删除已有历史记录。
- PostgreSQL 仅用于记录操作用户、提交哈希、操作类型和时间等辅助信息，文章历史正文仍以 Git 为准。

# 十、成员管理

后台需要维护网站成员。

成员至少包含：

- ID
- 姓名
- 头像

文章只保存成员 ID。

网站展示时再解析成员资料。（网站中已经有成员姓名.md了，可以在这个基础上加入ID。）
当成员有重名的，比如dongjiahui，那另一个就叫dongjiahui1，再有重名的就dongjiahui2，一次类推。

普通成员不能直接发布正式文章。

管理员可以审核、驳回和正式发布文章。

# 十五，部署架构要求

### 总体要求
采用 Docker Compose + GitHub + GitHub Actions 自动部署方案。

目标：

- 支持一键迁移至任意 Linux 服务器。
- GitHub 为唯一代码源（Source of Truth）。
- 服务器不得被人工直接修改项目文件；后台服务可以通过受控程序修改 Markdown，并自动提交到 GitHub。
- 所有部署均通过 GitHub Actions 自动完成，不允许手动修改服务器代码。

---

### 项目组成

网站由以下几部分组成：

- Nuxt 网站
- Docker Compose
- Markdown（Nuxt Content）
- 数据库（用户、权限等）
- 对象存储（S3协议图床，例如腾讯云COS，用于图片）
- GitHub Actions 自动部署

---

### 网站代码更新（Vue、Nuxt、Server API、CSS 等）

开发流程：

```
本地开发
    ↓
Git Commit
    ↓
Git Push
    ↓
GitHub Actions
    ↓
SSH 到服务器
    ↓
git pull
    ↓
docker compose build
    ↓
docker compose up -d
```

---

### 网站内容更新（Markdown）

管理员审核通过并正式发布后：

```
从 PostgreSQL 读取审核通过的草稿
    ↓
写入独立 Git 工作区中的 Markdown
    ↓
校验 Frontmatter 与 Markdown
    ↓
Git Commit
    ↓
Git Push
    ↓
GitHub Actions
    ↓
构建新镜像
    ↓
docker compose up -d
```

后台操作 Markdown 的 Git 工作区与 Docker 部署目录必须分离，避免正在运行的应用直接修改或重建自身。

---

### 数据存储要求

- Markdown 作为网站文章唯一数据源。
- 图片统一存储于S3协议图床，不存放于服务器。
- PostgreSQL 用于：
  - 用户
  - 登录状态
  - 角色与权限
  - 未发布草稿
  - 审核状态与驳回原因
  - 编辑锁
  - 操作审计
  - Git 提交哈希等发布记录
  - 评论（预留）
  - 系统配置（预留）
- 已发布文章正文不得以数据库作为正式数据源。
- 未发布草稿允许暂存于 PostgreSQL。

---

### 配置管理

所有配置均通过 `.env` 管理，包括但不限于：

- 数据库连接
- JWT Secret
- 腾讯云 COS 配置
- 域名
- 运行环境

禁止将敏感信息写入代码仓库。

---

### GitHub Secrets

GitHub Actions 所需敏感信息统一保存在 GitHub Secrets：

- SSH 私钥
- SSH 用户
- SSH 地址
- COS SecretId
- COS SecretKey
- JWT Secret
- 数据库密码

不得写入仓库。

---

### Docker 要求

Docker 镜像仅负责运行程序，不负责保存数据。

所有需要长期保存的数据均使用 Docker Volume 或宿主机目录挂载，包括：

- PostgreSQL 数据
- 后台专用 Git 工作区
- 日志（可选）

Markdown 不得同时以“镜像内副本”和“宿主机挂载副本”作为运行时数据源。

后台专用 Git 工作区与部署目录必须分离。

---

### 迁移要求

必须支持快速迁移至任意 Linux 服务器。

迁移流程应控制在以下步骤：

1. 克隆 GitHub 仓库。
2. 配置 `.env`。
3. 恢复数据库备份。
4. 执行 `docker compose up -d`。
5. 修改 DNS（如需要）。

迁移后无需修改项目代码即可正常运行。

---

### 开发目标

整个网站应做到：

- GitHub 为唯一代码源。
- Docker Compose 一键部署。
- GitHub Actions 自动部署。
- 易于升级。
- 易于备份。
- 易于迁移。
- 易于维护。

# 十八、Codex 开发与交接规范

## 18.1 Codex 运行环境

所有开发工作默认在开发者自己的电脑完成，不在生产服务器上直接运行 Codex。

推荐流程：

开发电脑 → Codex 修改代码 → 本地 Docker(PostgreSQL 等)测试 → 类型检查/测试/Production Build → Git Commit → Git Push → GitHub → GitHub Actions → SSH 自动部署服务器。

原则：

- GitHub 为唯一代码源。
- 所有代码先在本地验证，再提交 GitHub。
- 不允许在生产服务器上直接使用 Codex 修改源码。
- 生产服务器仅负责部署和运行。

## 18.2 本地开发要求

- PostgreSQL 使用本地 Docker。
- S3 使用测试 Bucket 或兼容服务。
- 不连接生产数据库。
- 不修改生产服务器。
- 所有环境变量使用开发环境 .env。

## 18.3 生产服务器职责

服务器只负责：

- Docker Compose 运行网站
- PostgreSQL
- GitHub Actions 自动部署
- 后台正式发布 Markdown
- 日志与备份

除部署和运维外，不直接修改源码。

## 18.4 Codex 项目交接文档

项目必须维护：

docs/CODEX_HANDOVER.md

每个阶段开始前必须阅读：

- 本需求文档
- docs/CODEX_HANDOVER.md

每个阶段完成后必须更新该文件。

至少记录：

- 当前完成阶段
- 修改文件
- 数据库变更
- API 变更
- 新增依赖
- 新增环境变量
- 架构设计决定
- 已知问题
- 下一阶段注意事项
- 禁止修改模块
- 给下一位 Codex 的交接内容

所有记录只允许追加，不允许删除历史。

## 18.5 Codex 开发原则

- 严格按阶段开发。
- 不跨阶段实现功能。
- 不随意重构已验收模块。
- 每阶段结束必须更新 CODEX_HANDOVER.md。
- 每阶段单独创建 Git Commit。

# 十九、项目文档规范

为保证项目长期可维护性，项目中必须维护以下文档：

```
docs/
├── ARCHITECTURE.md
├── CODEX_HANDOVER.md
└── CHANGELOG.md（可选）
```

## 19.1 ARCHITECTURE.md

该文档用于记录长期架构设计，除重大架构调整外原则上不修改。

至少包括：

- 系统整体架构
- 目录结构说明
- Nuxt Content 架构
- Markdown 与 PostgreSQL 的职责划分
- Git 与 GitHub 的职责
- Docker 部署架构
- GitHub Actions 自动部署流程
- S3 图片存储方案
- 权限模型
- 数据流
- 为什么采用当前技术方案
- 不允许轻易修改的核心设计

所有重大架构调整都必须同步更新此文档。

## 19.2 CODEX_HANDOVER.md

该文档用于多次 Codex 开发之间的交接。

每完成一个阶段必须追加记录，包括：

- 当前阶段
- 修改文件
- 数据库变更
- API 变更
- 新增依赖
- 新增环境变量
- 已知问题
- 下一阶段注意事项
- 给下一位 Codex 的说明

不得覆盖历史记录，只允许追加。

## 19.3 CHANGELOG.md（可选）

用于记录网站版本更新历史，例如：

- v0.1 完成后台登录

- v0.3 完成审核流程
- v1.0 第一版正式上线

该文档面向项目维护者和最终用户，不记录开发细节。
